How Jev!Jev handles data

Backstage does not save your cases, runs or keys to a file or database on our server.

Use made-up or redacted cases. Requests pass through our server, and its web server may hold them briefly while relaying. A case you run goes to each provider you select. This page describes what the application code does; it cannot promise what a provider or other infrastructure keeps.

How to get your data deleted

To request deletion of a ticket office row, open a GitHub issue quoting your ticket number, as the ticket form instructs. Do not put your email, case text or provider key in a public issue. An operator must handle the request because the code has no self-service deletion route. For a draft, sign out or close the tab. For a signed-in session, sign out to revoke it. A visitor with no GitHub account can instead email jev@breakoutwithai.com, quoting the reference only, never the status code, to have a question or a visitor sign-in row removed (for a sign-in row, say which Google account); a person removes it by hand.

What we keep

Ticket office. Watching the recorded shows needs no form and asks for no email. If you ask us to test your own decision, with your consent the form puts your ticket number, submission time, ticket type, email, optional website and idea, follow-up choice, consent flag and a code that stops a double submission in a database file on our server. Any show ticket issued before the form changed also holds the selected show. The form promises that these details are never shared or sold; the application code does not send ticket rows to another service.

Questions. If you send a question from the ask page, with your consent the same database file keeps a reference, the submission time, your email, your question, your two consent choices, its review state and any reply a person writes, plus two one-way fingerprints (hashes) of your status code. Your question is never sent to a model provider and no Jev run happens. Server log lines record only the reference and an outcome, never your email, question or status code. Your email is not checked and no reply is emailed to it. When a question is deleted, its row and review history leave the live database and only a fingerprint stays, so the same submission cannot come back. Copies made before a deletion, such as backups, are not changed, and the deleted bytes are not overwritten on disk. Until a period is approved, no retention period has been set and nothing is deleted automatically. To request deletion, email jev@breakoutwithai.com quoting your reference only; do not send your status code or post your question anywhere public. A person deletes it by hand.

TokenMax map board. Nothing leaves your browser until you press Share on the map page. Then a database file on our server keeps the tm-share/1 numbers that page showed you (mapper version, days, sources, sessions, cap episodes, output tokens and the two percentages), the alias you chose, the time you shared (the board shows only the day), a row id, and one-way fingerprints (hashes) of the page's random request key and of the request. Your network address is used in memory to limit request rates and is not stored with the row. The delete link shown after sharing removes your row. Rows have no automatic deletion date.

Sign-in. If Backstage sign-in is enabled, an operators file on our server holds approved email addresses, optional display names and password hashes. A signed session cookie contains the email and session details, is a cookie scripts cannot read, and lasts up to 12 hours. Signing out can add the session id and expiry to a file of invalidated sessions on our server. Google sign-in uses a short-lived cookie during sign-in.

Visitor sign-in. If you sign in with Google on the My questions page and your account is not an operator account, a table named visitors in the same private tickets database keeps your Google account id (sub), your verified email, the time you first signed in, the time you last signed in, a session generation value, a disabled marker that stays empty unless a person sets it, and the time you joined the waitlist, which stays empty unless you were put on it. Each question you send while signed in keeps your verified email, not an email typed into the page. Only you, signed in, can read your own questions and replies on that page; a person who reviews questions can read them too. The cookie __Host-jnj_visitor lasts 12 hours and holds a visitor id, an expiry and session values, but not your email or Google account id; signing out ends every session you hold. The first 10 visitors to send a question get one free question each; after that you can still sign in, you are put on a waitlist, and the My questions page shows your place. No email is sent to you and no model is called. Server log lines for visitors record a visitor id (the sign-in line also records your IP address and a request id), never your email, Google account id or question. There is no automatic expiry of visitor rows and no automatic deletion. To have yours removed, email jev@breakoutwithai.com; a person removes it by hand.

API tokens. A server file holds each token's id, label, a one-way fingerprint (hash) and creation time. The token itself is not stored there. Backstage server log lines for developer API requests include the token id.

Logs and trial accounting.

  • Backstage event logs go to server logs. They contain sign-in email and IP address, request ids, run provider and model, developer API route and status, and ticket ids or rejection reasons. They do not include case text in the event fields.
  • Page, sign-in and ticket office requests are logged by the web server; logging is off for the developer API, Backstage API and the Google sign-in return.
  • If a funded trial is available, its database file holds allowances, a keyed hash of your IP address, reservations, cost and day data; it has no case, question, answer or key column.

What we do not keep

Backstage does not write your cases, questions, answers, labels, runs, provider keys or coach key to its server files or databases. Your unfinished scene draft, including cases and question text, is saved in this browser tab's storage. It can survive a reload; sign out or close the tab to remove the draft. The active run and keys, including the coach key, are held in page memory. Clear keys stops further calls and clears the coach key too; signing out clears it as well. Closing the page loses the run. If you download records or run evidence, the browser saves your own copy.

The server temporarily reads each submitted case and key to relay a request. The statement above concerns files and databases written by this application; the web server may buffer a request or response briefly.

What leaves your browser

With your own key, the browser sends the case, question, choice definitions and your key through the Backstage server for each model you select. A funded trial, if ever switched on, uses our key instead. The server sends the request to that model's provider. A local keyword rule does not call a provider.

If you use the question coach, your browser sends the question you type and your coach key through our server to Anthropic or OpenAI, whichever you choose. It sends nothing else from your scene. The provider call uses your key, so any charge goes to your account. Our server does not save the coach question, key or reply to a file or database.

Draft starter cases sends the scene question and both answer names and their meanings, with your coach key, through our server to Anthropic or OpenAI, whichever you choose. Our server does not save them or the reply to a file or database.

How long

  • The scene draft lasts in this tab until you sign out or close the tab. A live run lasts only while the page stays open.
  • A sign-in session cookie has a 12-hour maximum age. The temporary Google sign-in cookie lasts 10 minutes. A funded trial cookie lasts 90 days.
  • Server settings request a one-day maximum for Backstage event logs and start a new log file each hour.
  • Funded trial accounting removes completed reservations and eligible allowances after 90 days, but keeps uncertain spending records for checking.
  • A visitor cookie lasts 12 hours. Visitor rows in the private tickets database have no automatic expiry and no retention period has been set.
  • The ticket office has no automatic deletion. The form says rows will be deleted by hand 90 days after the event ends; that is a plan, and the code does not carry it out.
  • Retention of the web access log and any temporary web server buffering is not set in this repository.

Not decided yet

  • We have not decided whether case data will be reused for internal testing or what rules would apply. The current server code has no such storage or reuse step.
  • We have not verified the form's never shared or sold promise for manual handling and infrastructure outside the application code.
  • We have not set a way to request deletion of operator accounts, invalidated session records, logs or trial accounting records, or to confirm a ticket deletion.
  • We do not know the retention and deletion policies of model providers or other infrastructure beyond the application code.
