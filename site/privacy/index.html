How Jev!Jev handles data

Backstage does not save your cases, runs or keys to a file or database on our server.

Use made-up or redacted cases. Requests pass through our server, and its web server may hold them briefly while relaying. A case you run goes to each provider you select. This page describes what the application code does; it cannot promise what a provider or other infrastructure keeps.

How to get your data deleted

To request deletion of a ticket office row and its lead sign-in records, open a GitHub issue quoting your ticket number, as the ticket form instructs. Do not put your email, link token, case text or provider key in a public issue. An operator must handle the request because the code has no self-service deletion route. For a draft, sign out or close the tab. For a signed-in session, sign out to revoke it.

What we keep

Ticket office. With your consent, the form puts your ticket number, submission time, ticket type, selected show, email, optional website and idea, follow-up choice, consent flag and a code that stops a double submission in a database file on our server. The form says, "We do not sell your details." The application code does not send complete ticket rows to another service. When mail is configured, it sends your email address to Google (Gmail) for sign-in link delivery.

Sign-in. If Backstage sign-in is enabled, an operators file on our server holds approved email addresses, optional display names and password hashes. A signed session cookie contains the email and session details, is a cookie scripts cannot read, and lasts up to 12 hours. Signing out can add the session id and expiry to a file of invalidated sessions on our server. Google sign-in uses a short-lived cookie during sign-in.

Lead email sign-in. When you request an email link, we keep your email and a SHA-256 digest of the link token, when it was created and expires, and whether it was used. After you confirm a link or sign in with Google, we keep a verified-lead record with your email, method, time and a random session credential generation. The raw link token is sent in the link, not stored in the database. We send your email address to Google (Gmail) to deliver a link when mail is configured.

API tokens. A server file holds each token's id, label, a one-way fingerprint (hash) and creation time. The token itself is not stored there. Backstage server log lines for developer API requests include the token id.

Logs and trial accounting.

  • Backstage event logs go to server logs. Auth event lines carry email and network address, including for link delivery and confirmation. Other events contain request ids, run provider and model, developer API route and status, and ticket ids or rejection reasons. They do not include case text in the event fields.
  • Page, some sign-in and ticket office requests are logged by the web server; access logging is off for the email link confirmation, developer API, Backstage API and Google sign-in return. Error logging is off for the email link confirmation because its address contains the token.
  • If a funded trial is available, its database file holds allowances, a keyed hash of your IP address, reservations, cost and day data; it has no case, question, answer or key column.

What we do not keep

Backstage does not write your cases, questions, answers, labels, runs, provider keys or coach key to its server files or databases. Your unfinished scene draft, including cases and question text, is saved in this browser tab's storage. It can survive a reload; sign out or close the tab to remove the draft. The active run and keys, including the coach key, are held in page memory. Clear keys stops further calls and clears the coach key too; signing out clears it as well. Closing the page loses the run. If you download records or run evidence, the browser saves your own copy.

The server temporarily reads each submitted case and key to relay a request. The statement above concerns files and databases written by this application; the web server may buffer a request or response briefly.

What leaves your browser

With your own key, the browser sends the case, question, choice definitions and your key through the Backstage server for each model you select. A funded trial, if ever switched on, uses our key instead. The server sends the request to that model's provider. A local keyword rule does not call a provider.

If you use the question coach, your browser sends the question you type and your coach key through our server to Anthropic or OpenAI, whichever you choose. It sends nothing else from your scene. The provider call uses your key, so any charge goes to your account. Our server does not save the coach question, key or reply to a file or database.

Draft starter cases sends the scene question and both answer names and their meanings, with your coach key, through our server to Anthropic or OpenAI, whichever you choose. Our server does not save them or the reply to a file or database.

If you use Google sign-in, sign-in also contacts Google's account services. This code does not tell us how long those services or model providers keep requests.

If you request an email sign-in link, we send your email address to Google (Gmail) for delivery.

How long

  • The scene draft lasts in this tab until you sign out or close the tab. A live run lasts only while the page stays open.
  • A sign-in session cookie has a 12-hour maximum age. The temporary Google sign-in cookie lasts 10 minutes. A funded trial cookie lasts 90 days.
  • An email sign-in link expires after 15 minutes and works once. Link and verified-lead rows have no automatic deletion schedule.
  • Server settings request a one-day maximum for Backstage event logs and start a new log file each hour.
  • Funded trial accounting removes completed reservations and eligible allowances after 90 days, but keeps uncertain spending records for checking.
  • The ticket office has no automatic deletion. The form says rows will be deleted by hand 90 days after the event ends; that is a plan, and the code does not carry it out.
  • Retention of the web access log and any temporary web server buffering is not set in this repository.

Not decided yet

  • We have not decided whether case data will be reused for internal testing or what rules would apply. The current server code has no such storage or reuse step.
  • We have not verified the form's no-sale statement for manual handling and infrastructure outside the application code.
  • We have not set a way to request deletion of operator accounts, invalidated session records, logs or trial accounting records, or to confirm a ticket deletion.
  • We do not know the retention and deletion policies of model providers or other infrastructure beyond the application code.
